## What's changed

One native pin moves: the stock libwebrtc under Mac Catalyst goes from `150.0.0` to `151.0.0`.
Nothing in the managed layer changes — the source is the same as
[2.17.2.6](https://github.com/sbokatuk/AntMedia.Net/blob/main/docs/release-notes/2.17.2.6.md).

### Mac Catalyst on libwebrtc M151

`AntMedia.Net.Mac` compiles Ant Media's iOS SDK against a stock community libwebrtc — their own
build is an iOS-only fork with no source, so no Catalyst slice can be produced from it. That stock
build is [stasel/WebRTC](https://github.com/stasel/WebRTC), and the daily upstream check filed
[#12](https://github.com/sbokatuk/AntMedia.Net/issues/12) when it published
[`151.0.0`](https://github.com/stasel/WebRTC/releases/tag/151.0.0) — WebRTC
[branch-heads/7922](https://chromium.googlesource.com/external/webrtc/+log/branch-heads/7922),
the engine behind Chromium M151 — while the build was still on `150.0.0`. This release closes it.

The integrity pin moves with the release. GitHub release assets can be deleted and re-uploaded
under the same name, so `fetch-mac.sh` verifies the download against a sha256 before using it:

```
WebRTC-M151.xcframework.zip
64a218fad3d84a0d783321aa9a1eec58ca266ac7879123f86b0b44b703b7d8dc
```

The hash was taken from the downloaded asset and agrees with the digest GitHub reports for it
independently, and with the checksum in the stasel release itself.

Verified rather than assumed: the archive carries the `ios-x86_64_arm64-maccatalyst` slice
`fetch-mac.sh` insists on, and the Catalyst build runs clean end to end against it — the Ant
Media SDK at the pinned commit compiles with the stock-libwebrtc shim, the xcframework is
produced, and both frameworks stage into the package. That is the leg a libwebrtc bump can break,
since the shim supplies what stock libwebrtc does not have (`RTCAudioDeviceModule` and the
factory initialiser Ant Media's Swift calls), and M151 still has neither — so the shim is still
needed and still fits. The Catalyst constraints from
[2.17.2.3](https://github.com/sbokatuk/AntMedia.Net/blob/main/docs/release-notes/2.17.2.3.md)
stand: Apple Silicon only, no external audio injection there.

stasel publishes no changelog of its own beyond the branch link above, and nothing in the M151
branch log is specific to this binding, so there is no headline feature to report — this is
keeping the engine current, and keeping the drift watch quiet.

### Packages

| Package | 2.17.2.7 |
| --- | --- |
| `AntMedia.Net.Mac` | libwebrtc `150.0.0` → `151.0.0`; the Ant Media commit and the shim are unchanged |
| `AntMedia.Net.Android` | unchanged — Ant Media `v2.17.2`, same `.aar` |
| `AntMedia.Net.iOS` | unchanged — Ant Media's own libwebrtc, same commit `47e2b02` |
| `AntMedia.Net`, `AntMedia.Net.Maui` | unchanged source |

Every package is republished at `2.17.2.7` all the same: `AntMedia.Net` pins its bindings to an
exact version and `AntMedia.Net.Maui` pins `AntMedia.Net` the same way, so one tag is five
packages. Apart from the Mac native payload and the version stamp, they are rebuilt from the
same inputs as 2.17.2.6.

## Upgrading

No API or behaviour changes. Android and iOS apps pick up nothing but a version number. A Mac
Catalyst app links a newer libwebrtc and should be run once against your server before
shipping, as with any engine update.

Everything in the
[2.17.2.6 notes](https://github.com/sbokatuk/AntMedia.Net/blob/main/docs/release-notes/2.17.2.6.md)
still applies.
