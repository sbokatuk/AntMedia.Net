## What's changed

Mac Catalyst moves to libwebrtc M156, and the Android client gets four fixes: a connect that could
freeze the main thread, a failed session that kept reconnecting for the life of the process, a
crash as a session starts, and a `TrackAdded` event that never fired. There are no public API changes. iOS is
unchanged — same Ant Media commit as
[2.17.2.6](https://github.com/sbokatuk/AntMedia.Net/blob/main/docs/release-notes/2.17.2.6.md).

### Mac Catalyst on libwebrtc M156

`AntMedia.Net.Mac` compiles Ant Media's iOS SDK against a stock community libwebrtc — their own
build is an iOS-only fork with no source, so no Catalyst slice can be produced from it. That stock
build is [stasel/WebRTC](https://github.com/stasel/WebRTC). This release moves it from `150.0.0`
to [`156.0.0`](https://github.com/stasel/WebRTC/releases/tag/156.0.0) — WebRTC
[branch-heads/8078](https://chromium.googlesource.com/external/webrtc/+log/branch-heads/8078),
the engine behind Chromium M156, and the newest stasel release.

`main` had been pinned to `151.0.0` in between, but that never shipped, and could not: on
2026-08-31 the `151.0.0` asset was replaced with different bytes under the same name, and a day
later the release was gone, so the Catalyst build failed with a 404. The upstream check reported
both on [#13](https://github.com/sbokatuk/AntMedia.Net/issues/13), which this release closes.
[`docs/BUILD.md`](https://github.com/sbokatuk/AntMedia.Net/blob/main/docs/BUILD.md#re-pinning-upstream)
now says what to do when a pinned stasel release disappears, and the daily check reports a failed
download as a download failure rather than as changed bytes.

The integrity pin moves with the release. GitHub release assets can be deleted and re-uploaded
under the same name, so `fetch-mac.sh` verifies the download against a sha256 before using it:

```
WebRTC-M156.xcframework.zip
43c2a6f7a650185bbc911d7605a979589671886e8fc0ac283f54fdf3f511dc46
```

The hash was taken from the downloaded asset, and agrees with the digest GitHub reports for it and
with the checksum in the stasel release itself.

**The shim is unchanged.** It supplies what stock libwebrtc lacks for Ant Media's Swift: an
`RTCAudioDeviceModule`, the factory initialiser it calls, and the `setCategory` overload it uses.
M156 still has no `RTCAudioDeviceModule`, and still has the other two. The header changes since
M150 (a new `RTCDtlsFingerprint`, some dropped `copy` attributes) touch nothing the shim or Ant
Media's code uses. The Catalyst slice's minimum OS stays at 14.0. The Catalyst constraints from
[2.17.2.3](https://github.com/sbokatuk/AntMedia.Net/blob/main/docs/release-notes/2.17.2.3.md)
stand: Apple Silicon only, no external audio injection there.

**A sandboxed Catalyst app needs `com.apple.security.network.server`** as well as `.client`.
WebRTC binds its own UDP sockets for media. Without the entitlement the server confirms the
publish, the app reports `publishing`, and no media ever arrives. The sample was missing it, and
now has it; the [README](https://github.com/sbokatuk/AntMedia.Net#readme) lists it. 2.17.2.6 on
M150 behaves the same, so this is not a change in the engine — but check your own app's
`Entitlements.plist`.

### Android: the websocket connect no longer freezes the main thread

The `autobahn` websocket library inside Ant Media's Android SDK waits on the calling thread four
times while it connects, with a bare `wait()` and a single `notifyAll()` from another thread. If
that thread gets there first, the wake-up is lost and the caller never returns — and the SDK calls
it on the main thread, so the app freezes, usually into an ANR. The connect also held the main
thread for as long as the TCP connect took: 2 minutes 14 seconds against an unreachable host.

`AntMediaClient` now runs the body of that connect on a background thread, with a watchdog that
recovers a lost wake-up. The SDK's own calls stay on the threads it requires, and the jar is
unchanged. ([#19](https://github.com/sbokatuk/AntMedia.Net/pull/19))

### Android: a stopped or failed session ends

`Stop()` used to call the SDK's `stop()` and drop the client. That only tells the server, and only
when the socket is up; the camera, the peer connection factory, the socket and the 5-second
reconnector are released elsewhere, in a call the SDK makes only when ICE disconnects after a stop.
A start that failed never got there, so the abandoned client called `connect()` every 5 seconds
for the life of the process, raised `Disconnected` each time, kept the camera on, and would have
published once the server came back.

`AntMediaClient` now releases every session it ends: at once if the server never confirmed it, and
on `publish_finished` or `play_finished` (or after 5 seconds) if it did. Fixed on the way
([#21](https://github.com/sbokatuk/AntMedia.Net/pull/21)):

- **A crash when a session starts.** The client opened the socket with `Init()` and then called
  `publish()`, which initialises again. The two could race on the shared peer connection factory
  and end the process with `PeerConnectionFactory has already been constructed`, or quietly build a
  second factory. The socket is now opened without initialising, so there is one `init()` per
  session.
- **A restart stopped the wrong stream**, because the stop read the id the new session had already
  set. **The stop after a failed start never reached the server.** **A retry with a preview
  attached threw `Already initialized`.** All three are fixed.

### Android: `TrackAdded` fires

`AntMediaClient.TrackAdded` had never fired on Android in any release with the cross-platform
client (2.17.2.2 to 2.17.2.6): the binding listened on an overload of `onNewVideoTrack` that the SDK
never calls. Remote video still showed, because the SDK attaches the renderer itself. It now fires,
on the SDK's signalling thread and before `PlayStarted`.

Two renderer fixes come with it ([#22](https://github.com/sbokatuk/AntMedia.Net/pull/22)). When a
remote track ends, the SDK now gets to release the renderer, so the next track in the same session
gets one. And a callback from a client that has been stopped, replaced or disposed no longer
touches the renderers, which carry over between sessions and see the same track ids every time.

## Upgrading

No API changes. Behaviour changes, all on Android unless stated:

- A websocket that takes longer than 10 seconds to connect fails with
  `AntMediaErrorCode.Disconnected`, within `AntMediaOptions.Timeout`. An unreachable host used to
  block the main thread until the TCP connect gave up, then report `Timeout`.
- After a failed start, `Disconnected` no longer keeps firing.
- A confirmed session stops its camera and closes its socket when the server answers the stop,
  rather than when ICE drops. `PublishFinished` after `Stop()` is unchanged.
- The camera and renderers start when the socket opens rather than before. An exception there fails
  `PublishAsync` instead of ending the process.
- `TrackAdded` now fires. If you worked around its absence, remove the workaround.
- Code that calls `WebRTCClient` from `AntMedia.Net.Android` directly does not get the connect fix,
  and can still freeze; use `AntMediaClient`.
- Mac Catalyst links a newer libwebrtc. Add `com.apple.security.network.server` to a sandboxed app,
  and run it once against your server before shipping, as with any engine update.

Everything in the
[2.17.2.6 notes](https://github.com/sbokatuk/AntMedia.Net/blob/main/docs/release-notes/2.17.2.6.md)
still applies.
